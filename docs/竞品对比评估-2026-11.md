## 一、PWORK 现状核对

### 1.1 产品形态

- 定位：装在本机的个人工作台，四步构成一个循环——速记与信源订阅（记下来）→ 搜索与投票筛选（加工）→ 周报月报与 PPT 生成（成稿）→ 快答复盘且行动项自动进待办（复盘）。数据全部存本机，无账号、无服务器、无遥测（[README](https://github.com/LoganLink0/pwork)）。
- 三种运行形态：开发模式、浏览器版（本地静态服务，可安装为 PWA）、桌面版（Tauri 2，Windows NSIS 中文安装包，macOS Apple Silicon dmg）（docs/project-overview.md）。
- AI 为可选项：16 家厂商 BYOK（国内 8 家、聚合 2 家、国际 5 家、本地 Ollama），Key 只写进本机文件，统一走本地网关（开发版 Node、生产版 Rust 内嵌，127.0.0.1:8788，带记账与三层降级）；不配 Key 时规则引擎兜底，全功能可用。
- 云端为可选项：使用者在自己的 Cloudflare 账号下部署 worker（定时抓源入 D1，北京时间整点调度表存 D1），应用内一键部署全程无终端；大陆网络下同步走 api.cloudflare.com 的 D1 直连，绕开 workers.dev 数据面阻断。

### 1.2 代码与规模（本地克隆实测）

| 项 | 事实 |
|---|---|
| 前端规模 | 243 个 TS/TSX 文件，约 1.35 MB 源码 |
| 依赖组合 | React 19、Vite 8、TypeScript 6、Dexie 4（IndexedDB）、Zustand、Tauri 2 API、vite-plugin-pwa、marked + DOMPurify、docx、pptxgenjs、mammoth、pdfjs、ffmpeg.wasm、tesseract.js（OCR） |
| 数据层 | Dexie schema v12，14 张表（notes / sources / items / reviews / actions / insights / tasks / goals / snapshots / blocks / profiles / caseFiles / aiCache / errorLog）；字段只增不删、软删除、实体必备 id / createdAt / updatedAt / schemaVersion |
| 分层 | pages → components/store → engine（纯逻辑，禁 import React）→ db，依赖方向单向 |
| 云端 | Cloudflare Worker + D1，独立测试基线 19 项 |
| 质量基线 | README 回归基线 529 项测试全绿、tsc 零错误；丢库恢复演练固化为测试；Mimosa 安全审计留痕 |

### 1.3 采集管线（输入模块的核心）

- 三级抓取通路：本地网关 `/rss` 服务端直抓（4MB/15s 上限，DNS 解析后拒内网与回环）→ 直连 → 转接服务兜底，逐源 10 秒超时。
- 筛选链：屏蔽词与标题过短预筛 → 指纹去重 → 四维规则评分（信源分级 / 新鲜度 / 兴趣词 / 实用词，权重固定零参数）→ stage 流转（raw→scored→kept/discarded）→ 当日 Top 10 分发（必看 / 可看 / 可略按同日排名分层）。
- 反馈回路：三档投票（多推 / 没想好 / 少推）驱动信源分级自动升降（多推率阈值，≥8 票才动）与 AI 兴趣词归纳（≥20 票启动、每 +15 票重跑、低估样本补课）；信源连败 3 次自动停用。
- 信源目录：11 个领域 80 个实测源（README 口径），CI 每周自动逐源验证活性；信源清单可导出 JSON 分享导入，按地址去重。

### 1.4 两项关键能力核实（源码检索证据）

- **OPML**：全源码无匹配。信源交换为自有 JSON 格式，与公共订阅生态互不连通（FreshRSS 与 Folo 均支持 OPML，见 3.2 节）。
- **正文全文抓取**：全源码无 Readability 或等价实现；Item 字段为标题、链接、摘要、指纹、评分、标注（app/src/db/collect.ts、cloudSync.test.ts），无 content 字段。

### 1.5 作者自录的已知边界（docs/architecture.md、docs/backlog.md）

- 多标签页同库并发为 last-write-wins，未做跨页协调。
- 评分链朴素（规则近似，可解释优先）。
- worker 与本地的「一天」口径不同（云端 UTC / 本地日），属文档化设计。
- 速记软删后云端 pwork_sync_records 旧 payload 不随 purge 删除，新设备首次初始化会以软删态拉回。
- AI 全库问答暂停（上下文只给检索标题导致答非所问），重启前置为正文级上下文与可选嵌入索引；DeepSeek 无 embeddings 端点已由作者核实。
- 手机浏览器连不到本机网关，手机侧 D1 拉取暂不通（docs/TODO.md 记录）。

## 二、市场定位：四个相邻品类

| 品类 | 代表产品（均开源） | 它们的强项 | PWORK 对应现状 |
|---|---|---|---|
| 本地优先工作台 | 思源笔记、AFFiNE、AppFlowy | 记录、编辑、同步、插件 | 采集管线强，编辑与插件缺位 |
| 订阅阅读器 | FreshRSS、Miniflux、Folo | 采集、过滤、客户端生态 | 筛选与产出回路强，阅读体验与交换标准弱 |
| 信息仪表盘 | Homepage、Glance、Dashy | 聚合展示、服务集成 | 仅快速启动卡，无小部件体系 |
| AI 第二大脑 | Khoj、Reor | 语义检索、连接器 | 检索为字面查询，嵌入索引缺位 |

四个品类各占一段能力。PWORK 是唯一把「采集 → 筛选 → 成稿 → 复盘」做成完整数据管线的开源产品；在每个单独品类里，成熟产品都明显更深。以下分品类展开。

## 三、分品类详细对比

### 3.1 本地优先工作台：思源笔记、AFFiNE、AppFlowy

**思源笔记**（AGPL-3.0，[官方仓库](https://github.com/siyuan-note/siyuan)）

- 数据全部存本地工作区文件夹（.sy JSON 文档）；官方云同步为付费订阅权益（年付含 8GB 云存储），S3/WebDAV 第三方存储同步同为会员功能；官方明示放入第三方同步盘会损坏数据（[定价页](https://b3log.org/siyuan/en/pricing.html)）。
- 插件市场收录 641 个插件（plugins.txt 清单逐行清点，[bazaar 仓库](https://github.com/siyuan-note/bazaar)），其中含 3 个 RSS 阅读插件。
- AI 经 OpenAI API 接入，用户自配 Key，属免费功能（官方仓库 Features 列表）。
- 移动端：Android / iOS / HarmonyOS 原生应用（App Store、Google Play、F-Droid）。

**AFFiNE**（社区版 MIT + 组件级 MPL 2.0 / EE 条款，[官方仓库](https://github.com/toeverything/AFFiNE)）

- 本地优先：桌面端数据存本机，无账号即可离线使用；同步经官方 AFFiNE Cloud（免费档 10GB、3 台登录设备，Pro 6.75 美元/月）；自托管免费（[下载页](https://affine.pro/download)、[定价页](https://affine.pro/pricing)）。
- 插件社区与第三方块官方自述「即将推出」，当前规模为零（官方仓库 README）。
- 官方云 AI 为付费附加订阅（8.9 美元/月）；自托管支持 BYOK（OpenAI / Anthropic / Gemini / FAL）并可开启 OpenAI 兼容自定义端点（[自托管 AI 文档](https://docs.affine.pro/self-host-affine/administer/ai)）。
- 已核对官方 README、下载页、定价页、自托管文档目录，均无 RSS 阅读或信源订阅条目。
- 移动端：iOS / Android 官方应用（官方定位为随手记录与查阅）。

**AppFlowy**（客户端 AGPLv3，[官方仓库](https://github.com/AppFlowy-IO/AppFlowy)）

- 本地数据为 SQLite 数据库；跨设备同步属 AppFlowy Cloud 服务；开源云后端仓库已停止维护，现行云端（含自托管版）构建于闭源商业代码库（[AppFlowy-Cloud 仓库](https://github.com/AppFlowy-IO/AppFlowy-Cloud)）。
- 官方云免费档：1 个协作工作区、2 成员、5GB、每月 20 次 AI 响应；Pro 10 美元/成员/月（[定价页](https://appflowy.io/pricing)）。
- 插件为 9 项内置功能集合；已核对官方文档索引与定价页，无第三方插件市场。
- 本地 AI 经 Ollama 接入（[官方博客](https://appflowy.com/blog/appflowy_local_ai_ollama)）。
- 移动端：iPhone 与 Android 10+ 官方应用。

**对照结论**：三家都满足「数据存本机」，同步路线分化明显——思源云同步完全收费，AFFiNE 有免费档且自托管后端开源（MPL 2.0 组件条款），AppFlowy 自托管后端已闭源。PWORK 的「服务端全开源 + 使用者自部署 Cloudflare 免费档 + 零预置账号」在三家中均无同型物。PWORK 的短板在两端：插件生态（641 对零）与原生移动端（三家全有，PWORK 为 PWA 且手机端数据通路受限）。信息采集方面仅思源能经市场插件实现 RSS，PWORK 的内置三级抓取通路在三家官方功能列表中均无对应物。

### 3.2 订阅阅读器：FreshRSS、Miniflux、Folo

**FreshRSS**（PHP 自托管服务端，[官方文档](https://freshrss.github.io/FreshRSS/)）

- 部署需 Web 服务器 + PHP 8.1+ + 数据库（推荐 PostgreSQL，支持 SQLite / MariaDB / MySQL），有 Docker 镜像（[环境要求](https://freshrss.github.io/FreshRSS/en/admins/02_Prerequisites.html)）。
- 客户端生态为同类最大：Google Reader API（官方定位效果最好）与 Fever API 两条接入路径，官方兼容客户端表格覆盖 Android / iOS / macOS / Linux / Windows 数十款应用（FeedMe、Read You、Reeder Classic、Unread、Fiery Feeds、NetNewsWire、Vienna RSS 等）（[移动访问](https://freshrss.github.io/FreshRSS/en/users/06_Mobile_access.html)）。
- 过滤：搜索运算符体系（intitle / inurl / 标签 / 日期区间 / 正则）+ filter actions（自动已读 / 收藏）+ 可保存复用查询（[过滤文档](https://freshrss.github.io/FreshRSS/en/users/10_filter.html)）。
- 全文抓取：内置 HTML+XPath、JSON 点路径网页抓取引擎；摘要源可配「原文 CSS 选择器」逐条抓正文（[抓取文档](https://freshrss.github.io/FreshRSS/en/users/11_website_scraping.html)）。
- 去重：核心内置「同源同标题」「同分类同 GUID」自动已读；扩展系统约 30 种钩子，官方扩展仓库带兼容性自动测试（[扩展开发文档](https://freshrss.github.io/FreshRSS/en/developers/03_Backend/05_Extensions.html)）。
- AI：核心无内建，靠扩展补齐（官方扩展 LLM Classification；第三方 Ai Summary、Feed Digest 等，[官方扩展仓库](https://github.com/FreshRSS/Extensions)）。

**Miniflux**（Go 静态编译单二进制 + PostgreSQL，Apache 2.0，[官网](https://miniflux.app/)）

- 定位极简（官方自述「Less is more」），部署即一个二进制 + PostgreSQL 9.5+（[环境要求](https://miniflux.app/docs/requirements.html)）。
- 客户端生态：官方列出约三十个第三方客户端（Capy Reader、Read You、FeedMe、NetNewsWire、Unread、Reeder Classic、Newsboat 等），经自有 REST API、Fever、Google Reader 兼容子集三条路径接入（[第三方应用](https://miniflux.app/docs/apps.html)）。
- 过滤：三层规则——feed 级 RE2 Block/Keep 正则、Entry Filtering（字段 + 日期模式，含 max-age 时长条件）、内容重写与 URL 重写内建规则库；被 Block 的条目直接不写库（[规则文档](https://miniflux.app/docs/rules.html)）。
- 全文抓取：Scraper Rules（CSS 选择器，内建常用站点规则库）+ feed 级 crawler 开关（同一页面）。
- AI：已核对的官方核心文档范围内无内建 AI 记载；官方应用列表收录 Miniflux-ai（Ollama / ChatGPT 等生成摘要）等外部集成（[第三方应用](https://miniflux.app/docs/apps.html)）。核心去重能力在已核对页面范围内未见官方记载。

**Folo**（AGPL-3.0，客户端型产品 + 官方云端服务，[官方仓库](https://github.com/RSSNext/Folo)）

- 客户端覆盖全平台：Web、iOS、Android、macOS、Windows、Linux（桌面端 Electron，移动端 Expo/React Native）；订阅、已读状态、星标经官方账号体系跨设备同步；已核对 README 与 follow.is，未见自部署服务端与公开同步协议记载。
- AI 为内建一等能力：对单篇 / 订阅源 / 文件夹 / 全部订阅提问（可自带 Key、可接 MCP）、时间线摘要、四语对照翻译、定时 AI 简报投递聊天或邮箱；Actions 规则对新条目执行 filter / star / rewrite / notify / summarize（官方 README）。
- 订阅范围：RSS / Atom / JSON feed、数千 RSSHub 路由、newsletter 专用收件邮箱、OPML 导入导出（官方 README）。

**对照结论**：PWORK 的差异在「读后回路」——投票驱动信源分级、AI 兴趣词归纳、条目转行动卡进任务库、复盘回路，三家阅读器均无这一段（Folo 的 Actions 与 AI 简报是同类里最接近的，止步于通知与摘要投递）。PWORK 的差距集中在四点：公开同步协议与第三方客户端生态（数十款对零）、过滤规则表达能力、原文正文抓取、OPML 交换标准。移动阅读体验在阅读器品类由第三方客户端生态承担，PWORK 需要自建移动通路（见五.1）。

### 3.3 信息仪表盘：Homepage、Glance、Dashy

- **Homepage**（[官网](https://gethomepage.dev/)）：定位「集成 100+ 服务」的应用仪表盘；服务小部件文档清单 164 项（当日逐项清点），信息类小部件 13 种（RSS / Hacker News / Reddit 需经服务集成覆盖）；多文件 YAML 配置 + Docker label 自动发现；dark/light 加 22 种配色、Custom CSS/JS 注入；settings 文档设 PWA 专章（[settings](https://gethomepage.dev/configs/settings/)）。
- **Glance**（[官方仓库](https://github.com/glanceapp/glance)，37.3k stars）：Go 单二进制（小于 20MB）；28 种小部件，RSS、Hacker News、Reddit、Lobsters、YouTube、Twitch、行情、天气全部原生提供，信息流聚合覆盖为三者最完整；YAML 保存自动重载；README 设移动端优化专节（[配置文档](https://github.com/glanceapp/glance/blob/main/docs/configuration.md)）。
- **Dashy**（[官网](https://dashy.to/)，26.8k stars、21.9M Docker 下载）：小部件文档目录 92 项（通用 39 / 自托管服务 32 / 系统监控 16 / 动态 5），含 RSS Feed 与 Hacker News；40+ 内置主题与界面调色器；界面内编辑配置写回磁盘；端到端加密云备份（Cloudflare Worker + KV）；README 声明响应式界面与 PWA 基础离线访问（[widgets 文档](https://dashy.to/docs/widgets)）。

**对照结论**：仪表盘品类止步于「展示」——28 至 164 种小部件没有后续加工链路。PWORK 在此品类只取了「快速启动 + 今日概览」一小块；若把它当起始页使用会全面落后（Glance 原生信息流小部件对 PWORK 的无小部件体系），但 PWORK 的日报条目会进入评分、投票、成稿与复盘，两类产品的终点不同。此品类的参照价值在信源类型广度：行情、天气、Reddit 等类型可作为 PWORK 信源适配器接口（见五.5）的候选类型清单。

### 3.4 AI 第二大脑：Khoj、Reor

**Khoj**（AGPL-3.0，[官方仓库](https://github.com/khoj-ai/khoj)、[文档站](https://docs.khoj.dev/)）

- 自托管时索引与搜索全部在本机；云端版嵌入向量与原文存 AWS 私有云 Postgres，按用户 ID 分片；匿名遥测发 PostHog，自托管可关闭（[隐私页](https://docs.khoj.dev/privacy)）。
- 检索：基于 Transformer 的语义搜索与嵌入向量，支持增量搜索与查询过滤器（[功能总览](https://docs.khoj.dev/features/all-features)）。
- 连接器：Obsidian 与 Emacs 自动同步、Notion 与 GitHub 凭据同步、桌面应用文件持续同步、网页拖拽上传；联网检索默认 JinaAI reader，可选 Serper / Olostep（[数据源](https://docs.khoj.dev/data-sources/share_your_data)、[联网检索](https://docs.khoj.dev/features/online_search)）。
- 模型接入：自托管原生支持 GGUF 本地模型、可连 Ollama、经 LiteLLM 接自带 Key 的商业模型；云端版限第一方模型（[Ollama 文档](https://docs.khoj.dev/advanced/ollama)）。
- 客户端：桌面应用（可装 PWA）、网页、Obsidian 插件、Emacs 包、WhatsApp；移动端经 WhatsApp 与手机浏览器（文档 clients 分类无独立 iOS/Android 应用页面）。

**Reor**（[官方仓库](https://github.com/reorproject/reor)）

- 维护状态：仓库 2026-03-07 被所有者归档转为只读；最后提交 2025-05-13；最新版本 v-0.2.32（2025-04-05）；README 指引的官网域名已失效（[提交历史](https://github.com/reorproject/reor/commits/main)）。
- 全部数据在所选目录的 markdown 文件；笔记分块嵌入 LanceDB 本地向量库，相关笔记按向量相似度自动连接，LLM 问答基于 RAG；本地优先设计，设置内直连 Ollama，嵌入经 Transformers.js 本地生成（官方 README）。
- 从其他应用导入需手动放入 markdown 文件；应用间集成 README 写明 coming soon。

**对照结论**：PWORK 的跨库检索目前为字面查询（Ctrl+K 命令面板），嵌入索引缺位，作者已把「正文级上下文 → 可选嵌入索引」列为 AI 全库问答的重启前置。Khoj 证明本地语义检索可以常规化交付（自托管时嵌入本机生成），Reor 的 LanceDB + Transformers.js 组合是纯本地方案的参考实现（引用时注意项目已归档）。PWORK 的优势在数据主权与 AI 通路的透明性：Khoj 云端版数据出设备，PWORK 的 BYOK 全本地网关、外发内容明示、记账可查在同类中最彻底；此外 PWORK 的 AI 面向「产出」（筛选、调研、成稿、复盘教练），第二大脑品类的 AI 面向「问答」，两侧的落点不同。

## 四、优势（专家视角）

**1. 管线完整性在开源世界无同型物。** 阅读器的产出端止步于导出与推送（FreshRSS 的 filter actions 与 Webhook、Folo 的 Actions 规则），工作台品类无内置订阅（仅思源可装市场里的第三方 RSS 插件），仪表盘止步于展示。PWORK 把「读完之后怎么办」做成了系统能力：投票驱动信源分级、多推率回传、AI 兴趣词归纳、条目转行动卡进任务库、复盘回路，每一段都有测试覆盖。这属于差异化定位，追赶者需要重做整条管线。

**2. 数据主权的彻底程度处于同类最彻底一档。**

| 产品 | 服务端与数据归属 |
|---|---|
| PWORK | worker + D1 全开源自部署，零预置账号，AI Key 只存本机文件，外发内容明示 |
| 思源 | 官方云同步为付费订阅，S3/WebDAV 为会员功能，官方明示第三方同步盘会损坏数据 |
| AFFiNE | 官方云免费档 10GB/3 台设备；自托管免费，后端社区版 MPL 2.0 |
| AppFlowy | 开源云后端仓库停止维护，现行云端为闭源商业代码库 |
| Khoj | 云端版嵌入向量与原文存 AWS Postgres；自托管时全本机 |
| Folo | 订阅、已读、星标同步经官方账号体系，已核对官方渠道未见自部署服务端记载 |

**3. 大陆网络适配是海外产品普遍缺位的真实价值。** D1 直连绕过 workers.dev 数据面阻断、16 家 AI 厂商以国内为优先、Gitee 镜像、信源目录以国内可达源为主、转接服务可自建。FreshRSS / Miniflux / Folo 的官方文档均无这类约束的应对设计。

**4. 工程纪律达到成熟团队水准。** 529 项测试、丢库恢复演练固化为测试、安全审计留痕、错误日志全链路、engine 纯逻辑层禁 import React、ADR 与复盘制度化。同类个人项目 Reor 已于 2026-03 归档只读，PWORK 的迭代密度远高于它归档前的水平。

## 五、差距与对策（按影响排序）

### 5.1 移动端数据通路（最硬的差距）

- **差距**：三家工作台全部有原生 iOS/Android 应用（[思源](https://github.com/siyuan-note/siyuan)、[AFFiNE 下载页](https://affine.pro/download)、[AppFlowy](https://github.com/AppFlowy-IO/AppFlowy)）；PWORK 手机端受「手机浏览器连不到本机网关」限制，手机侧 D1 拉取暂不通（docs/TODO.md）。信息采集类产品的核心场景（通勤刷日报、随时速记）恰好是移动场景。
- **对策**：手机端放弃「本地网关必然可达」的假设，读写全部走 api.cloudflare.com 的 D1 查询端点（`POST /accounts/{账户}/d1/database/{库}/query`，请求体 `{sql, params}`，[官方 API 文档](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/)；桌面端 cloudSync.ts 的 d1Query 已在用同一端点执行只读 SQL）。投票、批注、速记追加的写语句走同一端点（官方定义为 SQL 执行入口；写语句行为与令牌的 D1 编辑权限组在实施时按该页核对），写入 pwork_sync_records 后由既有记录级增量同步收敛到各设备。worker 补齐写端点作为海外与自有域名的直连路径。手机端不跑本地网关，AI 保持桌面独占的既定边界。手机 PWA 由此成为完整客户端。

### 5.2 检索无嵌入索引

- **差距**：Ctrl+K 为字面查询；作者自录 AI 全库问答暂停，重启前置为正文级上下文与可选嵌入索引（docs/architecture.md）。
- **对策**：按 docs/TODO.md 已有评估实施——bge-small-zh-v1.5 ONNX（作者已评估约 100MB）在本地网关进程内运行（DeepSeek 无 embeddings 端点已由作者核实，嵌入走本地是既定约束下的正确路线）；索引文件可随时重建、排除在备份之外；入库、投票、编辑时增量嵌入；Ctrl+K 改为字面与向量双通道混合排序。参考实现：Reor 的 LanceDB + Transformers.js 本地向量组合（项目已归档，仅作实现参照）；Khoj 自托管时嵌入本机生成的实践证明此路线可常规化交付。

### 5.3 条目无正文全文

- **差距**：Item 字段止于标题、链接、摘要、指纹、评分、标注（app/src/db/collect.ts）；FreshRSS 内置 CSS 选择器与 HTML+XPath 抓取引擎（[文档](https://freshrss.github.io/FreshRSS/en/users/11_website_scraping.html)），Miniflux 有 crawler 与内容重写规则库（[规则文档](https://miniflux.app/docs/rules.html)），PWORK 无对应能力（源码检索证据见一.4）。
- **对策**：网关新增 `/extract` 端点：服务端抓取条目原文，用 @mozilla/readability 提取正文——官方 README 明示此为 Firefox 阅读模式同款库，npm 包名 `@mozilla/readability`（Apache-2.0），`parse()` 返回 title / content / textContent / excerpt / byline / publishedTime 等字段，并建议输出经 DOMPurify 消毒（[官方仓库](https://github.com/mozilla/readability)）；PWORK 已引入 DOMPurify，消毒环节零新增依赖。正文存入新字段 content（字段只增不删，符合数据层铁律），复用网关既有 4MB/15s 守卫与 URL 防护；抓取失败保留摘要字段不动并就地记录错误。正文同时服务 AI 问答上下文、周报引用与全文检索——它是 5.2 的前置依赖。

### 5.4 交换格式缺 OPML

- **差距**：信源导入导出为自有 JSON（源码检索证据见一.4）；OPML 是订阅清单的公共标准，FreshRSS（[订阅文档](https://freshrss.github.io/FreshRSS/en/users/04_Subscriptions.html)）与 Folo（[README](https://github.com/RSSNext/Folo)）均支持。
- **对策**：浏览器端 DOMParser 读、XMLSerializer 写，零新增依赖；PWORK 的 80 个实测信源包由此进入公共订阅生态，外部订阅清单也能一键导入。

### 5.5 无扩展点

- **差距**：思源插件市场 641 个插件；FreshRSS 提供约 30 种钩子与系统/用户两级扩展（[扩展文档](https://freshrss.github.io/FreshRSS/en/developers/03_Backend/05_Extensions.html)）；Glance 有 iframe、html、extension、custom-api 四种自定义途径（[FAQ](https://github.com/glanceapp/glance)）。PWORK 全封闭，单人开发无法覆盖所有信源类型与集成目标。
- **对策**：把 `fetchFeed` 三级通路的输入端接口化为信源适配器（RSS 与 yt-dlp 已验证两类源型），这是收益最高的第一个开放点；导出目标（Obsidian 日报已有）作为第二组接口。规则自动化的设计参照 Folo 的 Actions（filter / star / rewrite / notify / summarize）；钩子粒度参照 FreshRSS。仪表盘品类的小部件体系不必追——品类定位不同，其信息源类型清单（行情、天气、Reddit 等）可作适配器的候选类型来源。

### 5.6 过滤表达力上限

- **差距**：Miniflux 三层 RE2 规则与日期条件（如 `max-age:7d`，[规则文档](https://miniflux.app/docs/rules.html)），FreshRSS 有完整搜索运算符与正则体系（[过滤文档](https://freshrss.github.io/FreshRSS/en/users/10_filter.html)）；PWORK 只有屏蔽词预筛加固定权重评分，作者自录「评分链朴素」。
- **对策**：屏蔽词升级为规则集（正则、字段限定、时间窗），投票闭环继续作为零参数默认路径，规则集作为覆盖层，两者叠加生效。

### 5.7 测试持续集成未建立

- **差距**：信源活性已有每周 CI（README），529 项测试与 tauri build 的 GitHub Actions 尚缺（docs/backlog.md 列为缓办，macOS 出包工作流在 docs/TODO.md 待办）。外部贡献者提交 PR 时，回归保障目前依赖作者本机手动执行。
- **对策**：macOS 出包工作流动工时，一并建立测试工作流（vitest 529 项 + tsc -b + worker 19 项），使外部贡献的每次提交都有回归保障。

### 5.8 已知边界若干（作者已自录，不重复展开）

多标签页 last-write-wins、跨设备一致删除待设计、UTC 与本地日口径、速记软删 payload 滞留云端（[docs/backlog.md](./backlog.md)）。

## 六、十倍规模检验（数据量、调用频率、用户规模各乘以十）

- **真实红线在查询路径**：`itemsOfLocalDay` 与 `digestDates` 执行 `db.items.toArray()` 全表扫描后内存过滤（app/src/db/collect.ts）；5 万条实测无恶化，50 万条时日报页每次进入都会全表拉取。信源数量乘以十后必然触发，需要改为 `where('fetchedAt').between(...)` 索引区间查询。
- 投票闭环乘以十：样本更大，信源分级与兴趣词归纳更稳，成立。
- 云端 cron 乘以十（80 源 → 800 源）：每小时一轮的频率与 D1 写入量仍在安全区间；AI 筛选成本由使用者 BYOK 自担且透明，成立。
- 单人支持成本乘以十：安装失败、签名警告、杀毒软件误报的咨询量会先于任何技术红线到达；更新器托管源（签名密钥已备，待拍板）与代码签名证书届时从决策项转为必选项。

## 七、判断与优先级

- 差距清单里没有一条动摇产品定位；管线完整性、数据主权、大陆适配、工程纪律四个优势都有可回溯的证据支撑。
- 时间敏感两项：**移动端数据通路**（信息采集产品的核心场景缺口）与**测试持续集成**（macOS 出包与外部贡献的窗口期）。
- 依赖排序：正文全文提取先行（嵌入检索与 AI 全库问答共用其产出），嵌入索引紧随；OPML、信源适配器接口、规则集覆盖层相互独立，可按容量穿插。
- 仪表盘品类不构成竞争关系，小部件体系不在建议范围；其价值仅限于为信源适配器提供候选类型清单。
