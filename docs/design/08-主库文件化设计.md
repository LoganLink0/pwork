# 08 · 主库文件化设计（送审稿）

> 状态：**设计送审，未动工**。批准后按「分阶段交付」执行，每阶段独立可用。
> 决策依据：05-路线图 0.3「桌面主库文件化」条目；AGENTS 设计规则 3a（三问）；W3 决议 C-3 的伏笔（「StorageAdapter 推迟至 SQLite 时引入」——本文即该伏笔的兑现设计）。

## 1. 目标与非目标

**目标**（按用户价值排序）：

1. **数据常态即文件**：桌面版用户的全部业务数据落在应用数据目录的**人类可读、通用工具可直接处理**的存储中——用户能用文件管理器看到、用任意备份工具拷走、离开 PWORK 时不丢数据。
2. **性能不降级**：四万五千项测试覆盖的功能在数万条记录下保持现有响应水平（现状：Dexie 打开后全量入内存，查询为内存过滤——新存储不低于此）。
3. **五条管线行为不变**：模块读写、备份（bundle v2 格式）、设备同步（记录级 LWW）、导入导出、测试基建——对外行为零变化，只换存储引擎。
4. **迁移安全**：老用户升级后数据零丢失、可回退。

**非目标**（明确不做，防止范围膨胀）：

- 浏览器版存储更换（IndexedDB 长期保留，见 §6）；
- 多设备实时协同（记录级同步的既有模型不变）；
- 编辑器级双链/实时渲染（与知识库产品正面对抗，非本项目定位）；
- 全文倒排索引（正文级检索沿用内存扫描，数据量级内够用——架构已知边界既有判断）。

## 2. 选型：三个候选与结论

### 方案 A：纯 SQLite（tauri 插件或 rusqlite 绑定）

- 单文件、事务、FTS5 全文检索。
- 致命伤 ×2：①**浏览器版无 SQLite**——要么 wasm SQLite（性能与复杂度代价大），要么双存储实现（每个读写两条路径，永久维护税）；②**记录级同步失效**——SQLite 整文件无法按记录做 LWW 增量，现同步模型要推翻重来。
- 结论：不采用为唯一方案。

### 方案 B：结构化文件目录（Markdown + JSON 混合，类 Obsidian vault）

- 每记录一文件（速记 md+frontmatter，任务/目标等 JSON 或 md），用户可见性最优；文件 mtime 天然支持增量同步。
- 致命伤：写放大（保存一条速记 = 重写一个文件，尚可）；**记录级同步的删除/重命名语义复杂化**（文件系统事件在三大平台行为不一）；查询=启动全量读入（与现状等价，可接受）；但 14 张表的 schema 演进（字段只增不删铁律）落在文件结构上，长期维护成本最高。
- 结论：不采用为存储引擎；但其**记录格式**被方案 C 的镜像层复用（可读档案已是雏形）。

### 方案 C（选定）：**桌面版 = SQLite 主库 + 文件镜像层；浏览器版 = 维持 IndexedDB**

- **SQLite 主库**：单文件 `pwork.db` 落应用数据目录，表结构与现 Dexie schema 一一对应（含 deletedAt/updatedAt/schemaVersion 全部字段）；事务写；行级updatedAt 天然支撑记录级同步（现模型的 SQL 化，同步管线只换存储适配）。
- **文件镜像层**：应用数据目录下 `vault/` 子目录，按**可读档案的既有格式**（§0.3d 已实现的 md+frontmatter 编解码复用）近实时投影速记/洞察/复盘等人类可读实体——用户看得见、Obsidian 可直接打开、任意工具可备份。镜像为**单向只读投影**（用户手改镜像不回写库——避免双向同步的冲突地狱；回写走正式导入通道）。
- **浏览器版**：IndexedDB 维持现状（StorageAdapter 的 Dexie 实现），无镜像层。桌面版的「文件即数据」是差异化主战场，浏览器版定位轻用/演示——这一刀把工程砍半，且不损失主叙事。
- 选型理由对照 3a 三问：①假如现成件全不存在，为「本地优先 + 记录级同步 + 用户可见数据」设计，SQLite（结构化查询与事务）+ 只读文件投影（人类可读性）是两个正交需求的各自最优解；②SQLite 在此是效率与能力选择，记录级同步模型原样保留，方案形状由需求决定；③数据 ×10（50 万条）：SQLite 单文件千万行级无压力，镜像层加增量投影即可——成立。

## 3. 目标架构

```
app/src/db/storage/
  adapter.ts        # StorageAdapter 接口（W3 C-3 伏笔的兑现）：按表 CRUD + 按表批量读 + 事务
  dexie-adapter.ts  # 现有 Dexie 实现的薄包装（浏览器版 + 迁移源）
  sqlite-adapter.ts # 桌面版 SQLite 实现（rusqlite 经 Tauri command 桥接）
  memory-adapter.ts # 测试用内存实现（全部 452 测试跑在它上面，行为等价证明）
  mirror.ts         # 文件镜像投影（桌面版专用，复用 readableArchive 编解码）
```

- **接口边界**：StorageAdapter 只暴露「按表的增删改查 + 批量 + 计数」，业务代码（store/engine）零改动——它们本就只经 db 层访问。
- **SQLite 桥接**：Tauri command（Rust 侧 rusqlite，库文件加 `pwork.db` 表 DDL 与迁移版本表）；JS 侧异步调用。单连接 + 互斥队列（现网关模式同款思路）。
- **镜像投影**：写事务提交后投递投影任务（防抖 2s 批量），崩溃安全——镜像永远是库的下游，损坏即整目录重建，不反向。

## 4. 迁移方案（老用户升级路径）

触发：桌面版启动时检测 `pwork.db` 不存在 **且** IndexedDB 有业务数据。

1. 弹一次性确认（说明发生了什么、耗时估计、可取消）；
2. IndexedDB 全量读出 → SQLite 事务写入（逐表行数对账，铁律 4「写库前后对账」）；
3. 对账通过 → 把迁移前状态导出一份 JSON 快照存 `migration-backup-<日期>.json`（回滚保险）→ 写 `pwork.db.meta` 标记完成；
4. 任何一步失败 → 删半成品库文件，回退 IndexedDB 模式运行，错误入日志并提示。

回退路径：设置 → 数据 提供「回到旧存储」（导出当前 SQLite → 清库 → 导入回 IndexedDB），保留两个大版本的退路。

## 5. 五条管线改动面清单（3.39 清单法）

| 管线 | 改动 | 不变 |
|---|---|---|
| 模块读写（store） | db 层实现替换为 adapter 分发 | store/engine 逻辑零改动 |
| 备份（bundle v2） | SQLite 逐表 dump 成既有 bundle 结构 | bundle 格式、导入通道、FUPAN 兼容全不变 |
| 设备同步（LWW） | 读写改走 SQLite 行；水位线/墓碑逻辑不变 | 记录级 LWW 模型、墓碑、云端协议不变 |
| 导入导出 | 走 adapter 写入 | 格式、对账报告、快照逻辑不变 |
| 测试基建 | 452 测试改跑 memory-adapter；新增 SQLite adapter 的结构/迁移专项测试 | 测试用例本体不改 |

**周边清点**：aiCache 与 errorLog（Raw 层）随 SQLite 一起迁（低频，直接搬）；kv 表（快照/键位/通知防重等）迁 SQLite kv 表；全局速记浮层、轮盘、命令面板等 UI 无感知。

## 6. 浏览器版策略

IndexedDB 长期保留为浏览器版的正式存储（StorageAdapter 的 Dexie 实现），无镜像、无迁移。浏览器版用户的数据带走能力由既有能力覆盖：全量导出、可读档案、OPML。介绍页如实表述：桌面版数据为本地文件 + 可读镜像；浏览器版数据在浏览器存储内，可随时导出。

## 8. 风险与开放问题

- **R1 rusqlite 桥接的序列化开销**：JS↔Rust 逐行往返在大批量导入时可能慢——缓解：批量接口一次传整表。开放问题：是否引入 msgpack 批量通道（S2 实测后定）。
- **R2 镜像层的磁盘占用**：数据双份（库 + 镜像）——缓解：镜像仅覆盖人类可读实体，二进制大对象（音视频产物）不入镜像；提供关闭开关。
- **R3 迁移期间的版本兼容**：迁移完成后用户回退旧版应用（0.1.x）会看不到新数据——发布说明必须写明「升级到 SQLite 版后不建议回退旧版」；迁移快照作为兜底。
- **开放问题 Q1（请拍板）**：镜像层是否包含条目（items，量大且机器性强）？倾向包含摘要与批注、排除 score 等纯机器字段。
- **开放问题 Q2（请拍板）**：SQLite 文件名与 vault 目录名——倾向 `pwork.db` / `vault/`，与现有 backups 同级。

## 9. 与既有决策的关系

- 兑现 W3 C-3 伏笔（StorageAdapter 推迟至 SQLite 引入）——当年的推迟使今天只需加一层适配，无需重构业务代码；
- 与 0.3 可读档案（md 格式）、备份 bundle（格式冻结承诺）复用而非重建；
- 与「数据只属于你」叙事的正面对抗点：完成后桌面版用户的 `%APPDATA%\com.pwork.workbench\` 下将同时存在 `pwork.db`（机器事实）与 `vault/`（人类事实），「离开自由」从导出动作变为常态事实。

## 10. 自检增补（送审后自查发现的实现级问题，2026-10-30）

以下问题在初稿中未覆盖或被轻描淡写，逐条补录应对方案：

### R4 事务边界无法跨进程桥接（S2 最大隐藏工程量）

- **问题**：现 Dexie 的 `db.transaction('rw', …)` 保证读-改-写原子性（速记并发竞态修复 1.1 就是靠它；导入对账也依赖事务）。SQLite 走 Tauri command 桥接后，**每次 invoke 是独立操作，跨 command 无法共享事务**——所有依赖事务的调用点都会静默丢失原子性。
- **应对**：盘点业务代码中全部 `db.transaction` 调用点（预计 5–10 处），逐个下沉为 Rust 侧复合 command（如 `update_note_fields` 单次调用内完成读-改-写）。S1 阶段的 memory-adapter 同步实现同款复合接口，测试锁原子性语义。**这是 S1 接口设计的硬约束：接口必须内置复合操作位，不能只暴露单行 CRUD。**

### R5 查询形状盘点缺失（S1 接口设计的真实复杂度）

- **问题**：初稿把接口定为「按表 CRUD + 批量」，但业务代码普遍使用 Dexie 链式查询（`.orderBy` / `.filter` / `.where` 复合索引）。这些查询形状若不进 adapter 接口，S1 阶段要么重写全部调用点、要么 adapter 实现一堆一次性方法。
- **应对**：S1 动工第一步 = 全量盘点 `db.` 查询形状（按表 × 操作 × 索引列输出一张清单），接口按清单设计，不预留猜测性通用查询。

### R6 时间戳格式红线

- **问题**：记录级同步按 `updatedAt` 的 **ISO 字符串比较**做 LWW。SQLite 若按其习惯存成 numeric epoch 或被 datetime 函数加工，字符串比较语义即被破坏，同步静默错序。
- **应对**：实现红线——时间戳字段一律原样存取 JS ISO 字符串（TEXT），**禁止使用 SQLite datetime/strftime 函数加工**；adapter 层单测锁死「存取往返字节不变」。

### R7 备份与 WAL 的不一致快照

- **问题**：SQLite 启用 WAL 后库文件旁有 `-wal`/`-shm` 伴生文件；自动备份若直接复制 `pwork.db` 文件，可能拷到未合并的事务状态，备份损坏。
- **应对**：自动备份改走 SQLite 原生 `VACUUM INTO`（产出一致性强快照文件）或 backup API；顺带升级备份管线为「SQLite 快照 + JSON bundle 双轨」（前者恢复即复制，后者跨版本兼容）。

### R8 镜像写失败策略

- **问题**：Windows 上 vault 文件可能被 Obsidian 索引、杀毒扫描等占用导致写失败；镜像写失败若阻塞主库写会拖垮核心路径。
- **应对**：镜像为纯下游——写失败进重试队列（防抖批量内自动重试），连续 3 次失败记错误日志（静默，不打扰），主库写永不等待镜像。

### R9 迁移中断恢复

- **问题**：迁移进行中用户强杀应用 → 半成品库文件残留，下次启动误判。
- **应对**：迁移前写独立标志文件（`migration-in-progress`），启动检测到标志 + 无完成标记 → 自动清理半成品重新迁移。

### R10 桥接开销与测试速度

- **问题**：每次 Tauri invoke 有序列化 + IPC 往返开销（约 0.1–1ms），批量导入（数万行）与大测试套件下累积显著。
- **应对**：批量接口分块（500 行/批）一次往返；S2 真机实测迁移与冷启动耗时，建立基线数字（顺带兑现 0.4 质量节的启动性能基线）。

### R11 安装包体积增量

- rusqlite + bundled SQLite 约增加 1–2MB 安装包体积——相对 51MB 基线可接受，留档备查。

## 11. 建议与本步并入的增量（边际成本低、收益显著）

1. **FTS5 正文检索**：SQLite 全文检索虚拟表（中文用 trigram tokenizer）——把 0.4 的「正文级检索」从 JS 内存扫描升级为数据库级，Ctrl K 与 AI 问答直接受益。S2 顺带实现。
2. **SQLite 原生备份双轨**：R7 的 `VACUUM INTO` 快照与 JSON bundle 并存，前者恢复=复制文件。
3. **启动性能基线**：借 SQLite 切换建立「冷启动到可交互」基线数字，纳入回归。
4. **Raw 层 TTL 清理 SQL 化**：errorLog/aiCache 的定期清理在 SQLite 中为一条 DELETE。

## 12. 开放问题倾向自答（供拍板参考）

- **Q1 镜像含条目**：倾向**包含**但简化——title + summary + 我的批注 + 链接，排除 score/fingerprint 等纯机器字段。条目是信息日报的核心内容，镜像（Obsidian 可直接打开）缺了它价值减半；机器字段的排除控制了体积。
- **Q2 命名**：维持 `pwork.db` / `vault/`，与 backups 同级。
- **Q3（新增，请拍板）**：迁移完成后旧 IndexedDB 数据保留一个版本周期再清理（防回退诉求），还是迁移成功即清？倾向**保留两个版本周期**，发布说明写明。
