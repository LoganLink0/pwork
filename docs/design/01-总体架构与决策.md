# 01 · 总体架构与决策

## 1. 四模块模型

```
输入 INPUT              处理 PROCESS           输出 OUTPUT
├─ 信息采集（舆情式）     ├─ AI 提纯/摘要         ├─ 报告/交付物
├─ 速记/笔记             ├─ 检索/知识整理        │
│                            │                  │
│         ↑__________________|__________________|
│        │          产出：洞察卡 · 行动项 · 修正目标
│        │
│   回路 REVIEW（复盘工作台）—— 第四模块，不是线性末端
│   消费：目标/计划（输入）、结果（输出）、外部信号（采集）
│   产出：认知更新（→输入/处理）、行动项（→输入）、假设校验（←采集信号）
```

**核心论证**：复盘消费输入与输出的数据，产出回流为下一轮输入。若当作线性末端，行动项无处落地、洞察无处消费，系统退化为年终仪式。因此工作台是**带反馈回路的闭环系统**，所有数据接口设计必须服务于这个环。

---

## 2. 集成方案选型

| 方案 | 说明 | 结论 |
|---|---|---|
| **A · 同壳模块（选定）** | 一个工作台应用壳，各模块为懒加载子路由/子应用，**共享数据层与设计系统** | ✅ 消灭数据孤岛；复盘工作台代码分层良好（engine/content/pages 分离），可迁移 |
| B · 独立应用 + 数据桥 | 各自独立部署，同源共享 IndexedDB 或导出桥接 | ❌ 每次都靠导入导出搭桥，摩擦杀死整合 |
| C · 本地后端化 | Tauri/Electron + SQLite | ⏸️ 数据治理能力最强、跨设备最顺；**作为采集伴生服务的自然演进**，不现在做死 |

**演进预期**：纯 Web（现在）→ 工作台壳 + 模块（W1–W3）→ 采集伴生服务引入本地后端（C4/W4+）→ 远期按需同步。每一阶段产品都完整可用。

## 4. 模块间数据流（闭环图）

```
输入：信息条目(采集) / 笔记(速记) / 目标与计划
   │                                    ↑
   │ raw→提纯                            │ 洞察卡 · 行动项 · 修正目标 · 假设校验
   ↓                                    │
处理：AI 摘要/打标/检索 ──→ 输出：报告/成果 ──→ 回路：复盘四步(C-L-A-P)
   │                                                    │
   └────────── O/T 候选池 · 信号触发复盘 · 预填数据 ←────┘
```

跨模块只允许 **ID 引用与导出物对接**，禁止直接读写对方数据表（字段所有权铁律，见 [02-数据治理规范](./02-数据治理规范.md)）。
